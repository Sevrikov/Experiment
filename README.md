# Experiment — аналоговые вычисления в памяти и AI-CAD

Репозиторий двух связанных тем, выросших из одного разговора:

1. **Аналоговый кроссбар** — модель решётки PCM, которая выполняет
   матрично-векторное умножение самой физикой, с калиброванной IBM моделью
   шума и дрейфа. Три интерактивных прибора плюс воспроизводимые замеры.
2. **AI-CAD** — спецификация мультиагентной системы, превращающей описание
   на естественном языке в валидную 3D-геометрию.

## Приборы

Все три выполняются целиком в браузере и опубликованы как артефакты claude.ai:

| Файл | Что показывает |
|---|---|
| [`artifacts/crossbar-3d.html`](artifacts/crossbar-3d.html) | Схема решётки: яркость каждого сегмента провода — вычисленный ток. Закон Ома даёт умножение, закон Кирхгофа — суммирование. Переключается на гелиевые микроканалы. |
| [`artifacts/crossbar-errormap.html`](artifacts/crossbar-errormap.html) | Полные 256×256 = 65 536 ячеек, живой прогон случайных матриц. Карта показывает, где копится ошибка, графики — почему там. |
| [`artifacts/crossbar-mnist.html`](artifacts/crossbar-mnist.html) | Обученная сеть живёт в проводимостях. Рисуете цифру, двигаете время — видите, как дрейф разъедает узнавание. |

## Откуда взята физика

Модель записи, дрейфа и шума чтения — **дословный перенос** формул и
коэффициентов из [IBM AIHWKit](https://github.com/IBM/aihwkit) (MIT), файл
`src/aihwkit/inference/noise/hermes.py`. Перенос сверен с оригинальным кодом
покоэффициентно: максимальное относительное расхождение `2·10⁻¹⁰`.

Коэффициенты откалиброваны IBM на кристалле HERMES Project Chip —
[Le Gallo et al., Nature Electronics 2023](https://www.nature.com/articles/s41928-023-01010-1).
Оттуда же системные характеристики: 64 ядра 14 нм, матрица 256×256 на ядро,
латентность MVM 133 нс, 1.55 TOPS/мм², 9.76 TOPS/Вт.

Проверить перенос самостоятельно: `python3 analog/verify_port.py` — клонирует
репозиторий IBM и сравнивает численно.

## Что показали замеры

### Классификатор живучее, чем следует из ошибки умножения

Сеть `256 → 64 → 10` на MNIST 16×16 (ровно 256 входов на 256 строк решётки),
точность в цифре 96.99 %. Прогон на всех 10 000 тестовых картинках:

| Срок с момента записи | Точность | Сохранено проводимости |
|---|---|---|
| сразу | 96.49 % | 100 % |
| 1 месяц | 95.95 % | 53 % |
| 1 год | 94.90 % | 45 % |
| 10 лет | 94.13 % | 38 % |
| 10 лет с компенсацией | 95.75 % | — |

Проводимость за десять лет проседает до 38 % от записанной, а точность теряет
2.9 пункта. Причина: `argmax` не чувствителен к общему масштабу, а `ReLU`
положительно однородна — равномерная просадка почти сокращается. Ломает
узнавание *разброс* дрейфа по ячейкам плюс смещения, которые остаются
цифровыми и не проседают вместе с весами.

### Рычаги, парно на одной матрице, срок год

| Рычаг | Эффект |
|---|---|
| Компенсация дрейфа | 93.0 → 95.3 % |
| Два устройства на вес вместо одного | 92.9 → 95.3 % |
| Нижний порог G, 0 → 30 % | 95.3 → 71.6 % (**вредит**) |
| АЦП 4 → 8 бит | 87.3 → 95.3 % |
| Второй слой в цифре | 95.3 → 96.5 % |

Слабее всех держится девятка: 93.1 % сразу и 86.4 % через десять лет, чаще
всего её принимают за четвёрку. Крепче всех единица — 99 % на любом сроке.

### Две ловушки, найденные при отладке

**Шкалу АЦП надо сажать на сигнал, а не на теоретический максимум.** Если взять
полную шкалу как «все 256 строк на максимальной проводимости», точность
обрушивается с 94 до 78 %. В дифференциальной схеме выход — это *разность*,
знаковые веса взаимно гасятся, и реальный размах на два порядка меньше.
АЦП тратит почти все коды на диапазон, куда сигнал не заходит.

**Нижний порог проводимости ведёт себя противоположно в двух схемах.** Для
беззнаковых весов он помогает (после компенсации), для знаковых в
дифференциальных парах — прямо вредит: порог поднимает *обе* ячейки пары, их
шумы складываются, а полезная разность нет.

### Python или C++

Вопрос был, писать ли сразу на C++. Замер (`bench/python_vs_cpp.py`):

```
Пустой вызов функции Python            0.13 мкс
  cut() булева разность OCC          3756 мкс   работы C++ в 29250× больше
  isValid() BRepCheck                 483 мкс   в 3761× больше
MVM 1024×1024  numpy(BLAS) 59 мкс   чистый Python 109 мс   разрыв ×1851
```

На булевой операции Python тратит 0.003 % времени: весь тяжёлый код уже
написан на C++ другими (OpenCASCADE, VTK, PyTorch, BLAS). Python бесплатен
там, где один вызов уходит в библиотеку хотя бы на ~10 мкс работы, и
разорителен в поэлементных циклах. Вывод: писать на Python, профилировать
`scalene` (он отдельно показывает время в Python и в нативном коде), и
переписывать только то, что он покажет красным.

## Чего в модели нет

Не смоделированы: падение напряжения на самих проводниках (на 256×256 это
существенно), залипшие ячейки, нелинейность АЦП, температурная зависимость.
Вход подаётся амплитудой, а реальный чип модулирует длительность импульса —
на результат умножения это не влияет, произведение то же.

Флюидный режим в `crossbar-3d.html` — **не от IBM**: это модель
Гагена–Пуазёйля по аналогии. Настоящий сверхтекучий гелий ей не подчиняется,
у сверхтекучей компоненты вязкость равна нулю и течение описывается
двухжидкостной моделью.
